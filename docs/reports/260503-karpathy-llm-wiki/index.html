핵심 결론

  1. 🧠 카파시 LLM Wiki의 본질은 검색 기술이 아니라 지식 운영체계임
  2. 📚 RAG처럼 매번 원본을 다시 뒤지는 대신, LLM이 읽은 내용을 Markdown 지식 자산으로 축적하는 구조임
  3. ⚠️ 다만 자동화보다 더 중요한 건 품질관리·출처관리·민감정보 필터링임

한 줄 정의

안드레 카파시가 제안한 LLM Wiki는 원본 자료를 LLM이 읽고, 사람이 읽고 수정할 수 있는 Markdown 위키로 재구성해 장기적으로 재사용하는 지식관리 방식이다.

단순히 “문서를 검색하는 시스템”이 아니라, 자료가 들어올 때마다 raw → page → index/log/schema → 재사용 루프를 돌려 개인 또는 팀의 지식이 복리처럼 쌓이게 만드는 운영 모델에 가깝다.

왜 중요한가

기존 AI 사용은 대체로 일회성이다. 문서를 올리고, 질문하고, 답을 받은 뒤 채팅이 끝나면 맥락도 함께 사라진다. 다음에 비슷한 질문을 하면 원본을 다시 올리고, 다시 설명하고, 다시 읽혀야 한다.

LLM Wiki는 이 낭비를 줄인다. LLM이 원본을 한 번 읽은 뒤 핵심 개념, 출처, 관계, 요약을 Markdown 페이지로 남긴다. 다음 질문에서는 원본 전체가 아니라 index.md, 질문 인덱스, 관련 page만 읽으면 된다.

즉, LLM Wiki의 핵심 가치는 기억이 아니라 재사용 가능한 구조화다.

RAG와 LLM Wiki 비교

항목RAGLLM Wiki
기본 방식원본을 청크·임베딩해 검색원본을 읽고 Markdown 위키로 재구성
저장 형태벡터 DB, 검색 인덱스, 원본 청크raw, pages, index, log, schema
사람이 읽기낮거나 도구 의존높음
수정 가능성파이프라인 재처리 필요 가능파일 직접 수정 가능
강점대량 문서 빠른 검색장기 축적, 편집, 맥락 연결
약점구조화·해석은 별도 필요초기 ingest와 품질관리 비용

둘은 완전한 대체 관계가 아니다. 대규모 검색은 RAG가 유리하고, 장기적으로 재사용할 핵심 지식은 LLM Wiki가 유리하다. 현실적인 조합은 검색 도구로 1차 후보를 찾고, 반복적으로 쓸 내용만 LLM Wiki page로 승격하는 방식이다.

실무 적용 구조

``text 원본 자료 raw/ ↓ LLM ingest ↓ 재사용 가능한 pages/ ↓ index.md / log.md / 질문 인덱스 / Graph Report ↓ 보고서·블로그·제품기획·투자판단에 재사용 ``

좋은 LLM Wiki는 단순히 파일이 많은 위키가 아니다. 다음 조건을 만족해야 한다.

  • 원본과 해석이 분리되어 있음
  • 출처가 명확함
  • 핵심 page가 hub와 연결되어 있음
  • 질문 기반으로 탐색 가능함
  • 중복, 깨진 링크, YAML 오류를 정기 점검함
  • 민감정보는 원문 재노출 대신 일반화함

Jeremy LLM-Wiki 현재 적용 상태

현재 LLM-Wiki는 카파시 방식의 파일 기반 구조를 Obsidian에 맞게 구현한 상태다. 핵심 구조는 raw/, pages/, index.md, log.md, schema/이며, 추가로 질문 인덱스와 Graphify v2를 붙여 탐색성을 강화했다.

최근 Graphify v2 기준 중심 노드는 다음과 같다.

중심 노드의미
LLM-Wiki 질문 인덱스질문 기반 진입점
제품 개발 지식 지도제품/PRD/MVP 활용 축
AI 지식 지도AI 학습·자동화·투자 허브
AI 자동화 운영 패턴실제 에이전트 운영 구조
LLM Wiki 운영 프레임워크카파시식 위키 운영 기준

이는 단순 자료 저장소를 넘어, 보고서모드·블로그 초안·제품기획·투자판단으로 이어지는 작업형 지식 베이스가 되고 있다는 뜻이다.

가장 큰 오해는 “LLM Wiki를 만들면 AI가 알아서 완벽히 기억한다”는 생각이다. 실제로 중요한 것은 자동 기억이 아니라, 기억할 가치가 있는 내용을 사람이 검토 가능한 구조로 남기는 것이다.

최종 판단

카파시 LLM Wiki는 개인 지식관리와 AI 에이전트 운영을 연결하는 매우 실용적인 패턴이다. 특히 Obsidian처럼 Markdown을 중심으로 쓰는 사람에게는 RAG보다 투명하고, 수정 가능하며, 장기적으로 축적되는 장점이 크다.

다만 성공 조건은 명확하다. 위키는 자동으로 좋아지지 않는다. 수집 → 선별 → ingest → 연결 → 점검 → 재사용 루프가 계속 돌아가야 한다.

따라서 Jeremy LLM-Wiki의 다음 단계는 자료를 더 많이 넣는 것이 아니라, 중심 허브와 질문 인덱스를 더 정교하게 만들어 “필요할 때 바로 꺼내 쓰는 지식 운영체계”로 다듬는 것이다.

실무 체크리스트

  • [ ] 새 자료는 raw에 저장하되, page 승격 여부를 선별한다
  • [ ] page는 반드시 hub 또는 질문 인덱스에 연결한다
  • [ ] 보고서/블로그/제품기획으로 재사용된 page를 우선 evergreen 후보로 본다
  • [ ] Graph Report 중심 노드를 주기적으로 확인한다
  • [ ] 민감정보·출처·중복 title을 자동 점검한다
